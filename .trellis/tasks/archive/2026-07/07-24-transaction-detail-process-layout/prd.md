# 资金流向详情两栏过程展示

## Goal

重构生活预算的“资金流向”弹层，减少当前总额卡、箭头和资金卡三段纵向占用，改成更紧凑的“详情 + 过程”信息结构，并为收入、支出和系统结转显示清晰的算式过程。

## What I Already Know

* 用户不希望继续使用当前三段纵向结构。
* 用户希望界面包含“一栏详情”和“一栏过程”。
* 过程采用可读算式，例如 `本周预算：610 元 - 42 元 = 568 元`。
* 支出截图当前显示“本周预算 ¥42 / 本周剩余 ¥568 → 支出总额 ¥42”。
* 收入截图当前显示“收入总额 ¥448 → 缓冲金 ¥448 / 缓冲金余额 ¥629”。
* 当前 `DailyTransaction.allocation` 保存本次变化金额，`balanceAfter` 保存交易后余额。
* 用户确认交易创建时本身就能获取交易前状态，因此新流水应同时保存真实 `balanceBefore`，不通过交易后余额反推。
* 旧流水缺少 `balanceBefore` 或 `balanceAfter` 时无法可靠生成完整的“前值 ± 变化 = 后值”算式。

## Confirmed Scope

* 本任务只调整生活预算资金流向弹层，不改变账务规则；仅扩展向后兼容的可选审计字段 `balanceBefore`。
* “详情”至少包含交易类型、备注、总金额、账目日期和创建时间。
* “过程”按实际发生变化的资金来源或去向逐条生成算式。

## Requirements

* 删除当前独立的“收入总额/支出总额”大卡、方向箭头和资金大卡组合。
* 弹层同屏展示上下两个紧凑区块：上方“详情”，下方“过程”，不使用标签页或左右分栏。
* “详情”区块内部只使用一行，包含交易类型、备注、账目日期/创建时间和总金额。
* 详情字段顺序固定为 `类型｜备注｜日期时间｜金额`，使用清晰分隔符。
* 两个区块使用左侧固定小标签、右侧内容的结构；“详情”标签对应单行内容，“过程”标签只出现一次并对应右侧多条算式。
* 详情单行不截断、不隐藏字段；宽度不足时仅详情内容区域允许横向滚动，弹层本身保持固定宽度。
* 收入、支出和结转共用同一套详情与过程结构。
* 新流水的过程必须展示资金部分名称、交易前余额、变化金额和交易后余额。
* 新流水在创建时同时保存不可变的 `balanceBefore` 和 `balanceAfter`，算式直接读取两份真实快照。
* 一次操作生成多条流水时，每条流水按真实执行顺序保存各自的交易前后快照。
* 多资金来源或去向交易在同一个“过程”区块内逐条显示，每个实际变化部分各一行算式。
* “详情”区块已经显示交易总额，“过程”区块不再增加重复的合计行。
* 每条过程固定使用单行格式：`资金部分：前值 ± 变化值 = 后值`，收入/转入使用加号，支出/转出使用减号。
* 每条过程不换行、不自动缩小字体；宽度不足时仅该算式行允许横向滚动。
* 资金缺口作为过程栏的例外行显示为 `资金缺口部分：未覆盖 ¥X`，不伪造前后余额算式。
* 新布局使用中性主题底色；只对运算符和变化金额使用语义色，收入/转入为绿色，支出/转出为红色。
* 钱袋名称、交易前余额、等号和交易后余额使用主题正文色，确保深色模式对比度。
* 过程行按实际资金执行顺序排列；系统结转先显示转出部分，再显示各转入部分。
* MVP 不提供算式复制、过程搜索或 Excel 过程字段。
* 旧流水缺少 `balanceBefore` 或 `balanceAfter` 时完全隐藏“过程”区块，只显示详情；不提示缺失、不回算历史余额。
* 过程中的加减方向必须与交易类型一致，不能只靠颜色表达。
* 深色与浅色模式都必须保持足够文字对比度。

## Decisions (ADR-lite)

### 交易前余额快照

**Context**: 虽然交易前余额可以从后余额和变化额反推，但创建交易时已经持有完整的变动前状态；复合结转也需要明确每一步的真实边界。

**Decision**: 新流水创建时同时保存不可变的 `balanceBefore` 与 `balanceAfter`。过程算式直接读取两份快照和 `allocation`，不做历史重放或数学反推。

**Consequences**: 类型、清洗、Excel 完整备份和交易审计 helper 需要支持 `balanceBefore`；旧流水缺少该字段时按既定规则隐藏过程栏。

### 详情与过程布局

**Context**: 当前总额卡、箭头和资金卡形成三段纵向布局，手机端高度较大；标签页又会隐藏其中一类信息。

**Decision**: 弹层同屏使用上下两个紧凑区块，上方展示“详情”，下方展示“过程”。不采用标签页或左右分栏。

**Consequences**: 用户一次打开即可看到交易信息和资金计算；实现需压缩内边距与重复总额信息，避免两个区块再次变成大卡片堆叠。

### 多部分计算过程

**Context**: 支出可能同时使用本周预算、缓冲金和后续周预算；收入也可能同时进入缓冲金和储备金。合并公式无法展示各部分交易后的真实余额。

**Decision**: 每个实际变化部分各显示一行独立算式。详情区块承担总金额展示，过程区块不重复显示合计。

**Consequences**: 多来源交易仍会有多行，但每行高度紧凑且可单独审计；不会恢复为多张大卡片。

### 旧流水过程

**Context**: 旧流水可能有 `balanceAfter`，但没有 `balanceBefore`，仍无法可靠展示真实交易前后余额；仅显示变化金额不符合用户对“过程算式”的定义。

**Decision**: 旧流水完全隐藏“过程”区块，只保留详情，不增加缺失提示，也不尝试回算。

**Consequences**: 新旧流水的弹层内容长度不同，但不会展示不完整或可能错误的算式。

### 详情单行布局

**Context**: 两行布局更易读，但用户希望详情本身只占一行，进一步降低弹层高度。

**Decision**: 详情区块将类型、备注、日期时间和总金额放在同一行。

**Consequences**: 详情内容可能宽于手机视口，需要局部横向滚动，且不得带动整个弹层横向移动。

### 详情溢出策略

**Context**: 单行同时承载类型、完整备注、日期时间和金额，窄屏无法保证全部自然排下。

**Decision**: 不截断或隐藏详情字段；详情区块内部使用单行横向滚动。弹层与过程区块保持正常宽度。

**Consequences**: 所有信息均可查看，但超长详情需要横向滑动；应隐藏或弱化滚动条，避免破坏移动端视觉。

### 详情字段顺序

**Context**: 单行详情需要固定阅读顺序，避免收入与支出使用不同布局。

**Decision**: 所有交易统一使用 `类型｜备注｜日期时间｜金额`。

**Consequences**: 收入、支出和结转详情一致；金额位于行尾，横向滑动时仍按自然语义顺序阅读。

### 区块标签位置

**Context**: 区块标题放在上方会增加高度，完全省略标题又会削弱详情与过程的边界。

**Decision**: 使用左侧固定小标签、右侧内容的两栏结构。“详情”右侧为单行，“过程”右侧为一条或多条公式。

**Consequences**: 标题清晰且不增加额外标题行；过程区需要让左侧标签与右侧首条公式自然对齐。

### 颜色与强调

**Context**: 继续使用大面积钱袋分类色会保留卡片堆叠感，完全单色又会削弱资金变化方向。

**Decision**: 两个区块使用中性主题底色；仅运算符和变化金额使用语义色。收入/转入为绿色，支出/转出为红色，其余文字使用主题正文色。

**Consequences**: 布局更像紧凑账本而不是多张彩色卡片；加减符号保证颜色之外仍有明确语义。

## UI Design Specification

1. **Purpose Statement**: 将资金流向弹层从三段大卡片压缩为可快速核账的两栏结构。用户打开弹层后，应在同一视野看到交易概要和每个资金部分的完整算式。
2. **Aesthetic Direction**: Brutally minimal，强调账本密度、数字节奏和计算可审计性；不增加装饰性卡片或复杂动画。
3. **Color Palette**: 沿用现有生活预算主题 token：正文 `#26342f` / 深色正文 `#edf2ea`，收入与转入使用 `#5f8d62` / `#83bd8b`，支出与转出使用 `#d88b7f` / `#dc8b82`，边框使用现有 `--life-border`。
4. **Typography**: 沿用项目字体 `Noto Sans SC`。详情使用紧凑粗体，算式数字使用统一字重与等宽感间距，不新增字体依赖。
5. **Layout Strategy**: 复用现有 BottomSheet。内容为两个非对称标签行：左侧固定窄标签“详情/过程”，右侧为可局部横向滚动的单行内容；过程右侧可以纵向容纳多条单行公式。
6. **Interaction**: 详情整行与每条公式可独立横向滑动，隐藏滚动条；弹层本身不横向移动。旧流水没有快照时省略整个过程栏。
7. **Icons and Motion**: 保留弹层标题的 Lucide 图标和现有入场动画；移除内容区箭头，不新增图标或动画。
8. **Brand Override**: 项目已有生活预算配色、Noto Sans SC 和 BottomSheet 规范，优先沿用，避免局部界面与现有产品割裂。

### 过程算式格式与溢出

**Context**: 数学算式被换行会破坏阅读顺序，自动缩小字体又会降低手机可读性。

**Decision**: 每个变化部分使用 `资金部分：前值 ± 变化值 = 后值` 的单行算式；收入/转入使用 `+`，支出/转出使用 `-`。单条过长时允许该行独立横向滚动。

**Consequences**: 过程含义稳定且可快速扫读；多来源交易会出现多条可横向滑动的紧凑公式行。

### 资金缺口过程

**Context**: 资金缺口不是实际钱袋，没有可审计的交易前后余额，但隐藏它会导致过程金额与交易总额不一致。

**Decision**: 过程栏使用例外行 `资金缺口部分：未覆盖 ¥X`，不显示虚构算式。

**Consequences**: 用户能看出未被任何资金来源覆盖的金额；过程渲染需支持普通算式行与缺口说明行两种形态。
