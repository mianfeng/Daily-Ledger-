# 逐笔资金流向详情

## Goal

为生活预算中的每一条收入、支出和系统结转流水增加可点击的详情视图，让用户能够审计这笔钱从哪里来、被分配或扣到哪些钱袋，以及交易完成后相关钱袋的余额。

## What I Already Know

* 用户希望点击任意一条明细进入资金流向详情。
* 收入详情需要显示收入分别去了哪里，以及分配后余额。
* 支出详情需要显示支出分别从哪里扣除，以及扣除后余额。
* 现有 `DailyTransaction.allocation` 已记录每笔流水对周预算、缓冲金、储备金、固定预留和提前动用金额的分配，可作为资金流向的权威依据。
* 现有流水没有保存交易完成后的钱袋余额快照；当前总余额不能直接代表历史交易当时的余额。
* 最近关键事件和全部事件目前只支持展示与删除，没有明细弹层。
* 系统结转也使用交易和 `allocation` 表达，适合纳入同一套审计详情。

## Scope

* MVP 先覆盖生活预算 `DailyTransaction`，不包含铜钱分账 `CopperTransaction`。
* 详情使用只读底部弹层，与现有移动端交互保持一致。
* “余额是多少”默认理解为该笔交易执行完成后，各受影响钱袋的余额，而不是当前余额。

## Requirements

* 最近关键事件和全部事件中的每条流水均可打开资金流向详情。
* 收入显示金额进入周预算、缓冲金、储备金、固定预留等去向。
* 支出显示金额从周预算、缓冲金、储备金、固定预留或提前动用中扣除的组成。
* 系统结转显示钱从哪个钱袋转出、转入哪个钱袋。
* 生活预算中的所有流水类型都纳入详情，包括主要收入、零散收入、退款报销、余额修正、普通支出、大额支出、固定支出、提前支付、周余额结转和周期缓冲金结转。
* 资金流向金额必须以交易保存的 `allocation` 为准，不根据当前设置重新计算。
* 新流水应能提供准确的交易后钱袋余额。
* 旧流水继续显示已有的资金流向，但不展示交易后余额，也不增加“历史余额未记录”等提示文案。
* 详情只展示该笔交易中实际发生金额变化的钱袋，不固定罗列未变化的钱袋。
* 支出的 `allocation.week` 与 `allocation.advance` 必须分别显示为“本周预算”和“后续周预算”，不得合并为笼统的“可消费余额”。
* 收入的 `allocation.week` 显示为“可消费余额”；收入侧不拆成本周与后续周，因为该分配可能覆盖整个预算周期。
* 新流水的余额快照需要分别支持本周剩余和后续周可用余额。
* 新流水保存的交易后余额是不可变的原始快照；删除或回滚其他历史流水时，不重算、不覆盖已有快照。
* 详情使用轻量箭头流表达方向：收入从总金额流向各去向，支出从各资金来源流向支出总额，系统结转从转出项流向转入项。
* 不新增独立详情按钮；点击流水条目打开详情。
* 删除入口继续只保留在流水列表中，详情内不提供删除按钮。
* 点击列表中的删除按钮只执行删除流程，不得同时打开详情。
* “查看全部”历史弹层初始展示最近 20 条，并提供“加载更多”；每次再加载 20 条，直到所有历史流水均可访问。
* 加载数量只属于临时 UI 状态，不写入 localStorage 或备份。
* 从历史流水弹层打开详情时，使用第二层详情弹层覆盖在历史弹层之上；关闭详情后返回原历史列表。
* 双层弹层必须保持明确的遮罩、层级和关闭边界，详情关闭事件不得同时关闭历史弹层。
* 新流水保存不可变的 `createdAt` 创建时间，详情显示“账目日期 + 创建时间”。
* 旧流水缺少 `createdAt` 时只显示账目日期，不增加缺失提示。
* 同一账目日期内，新流水按 `createdAt` 排序；缺少创建时间的旧流水使用现有稳定顺序作为回退。
* MVP 不提供历史搜索、类型筛选或从钱袋反查流水。
* 新流水在 `DailyTransaction` 内保存可选的不可变 `balanceAfter` 快照；`allocation` 仍是资金流、统计和删除回滚的权威数据。
* `balanceAfter` 至少能表达可消费余额、本周剩余、后续周可用、缓冲金、储备金和固定预留的交易后值。
* 一次操作生成多条流水时，必须按真实执行顺序逐笔保存中间快照，不能把最终状态复制到每一条流水。
* 当交易金额大于实际资金分配合计时，详情显示差额为“资金缺口”，不隐藏或伪造扣款来源。
* 本任务不因资金缺口而阻止记账，也不修改现有支出分配规则。
* 旧版 localStorage 和备份数据必须继续正常加载。

## Out of Scope (Explicit)

* 暂不修改任何资金分配或扣款规则。
* 暂不提供手动编辑资金流向。
* 暂不把资金流向做成独立报表或图表。
* 暂不覆盖铜钱分账 `CopperTransaction`；本任务只处理生活预算流水。

## Technical Notes

* 主要数据类型：`types.ts` 中的 `DailyTransaction`、`DailyTransactionAllocation`、`LifeBudgetPockets`。
* 资金分配与扣款逻辑：`lib/daily.ts` 中的 `allocateIncome`、`recordExpense`、`markFixedExpensePaid`、自动结转与删除回滚逻辑。
* 列表 UI：`components/DailyLedger.tsx` 中的“最近关键事件”和事件 BottomSheet。
* 持久化兼容：`sanitizeDailyData` / `normalizeAllocation` 必须容忍旧流水缺少新增快照字段。
* 当前未保存交易时间或同日流水的稳定顺序字段；历史余额回算不能只依赖日期排序。

## Technical Approach

* 扩展 `DailyTransaction`：新增可选 `createdAt` 和可选 `balanceAfter`；旧数据清洗时允许两者缺失。
* `balanceAfter` 保存完整的交易后审计快照，UI 再根据 `allocation` 只展示实际变化项。
* 收入的 `allocation.week` 映射为“可消费余额”；支出的 `allocation.week` / `allocation.advance` 分别映射为“本周预算” / “后续周预算”。
* 使用共享 helper 从交易执行后的预算状态和交易日期生成余额快照，避免每个收入、支出和结转分支手写字段。
* 对自动补做多周结转、周期缓冲金结转后紧接主要收入等复合操作，按交易执行顺序更新临时预算状态并逐笔生成快照。
* 详情展示完全由交易自身的 `allocation`、`balanceAfter`、类型和分类派生，不使用当前设置重新计算历史分配。
* 历史列表改为完整排序数据；主页面仅截取前三条，历史弹层通过组件状态每次展示 20 条。
* 点击流水行设置当前详情交易；删除按钮阻止事件冒泡。历史弹层打开时，详情使用更高层级的第二个 BottomSheet。

## Decisions (ADR-lite)

### 旧流水余额展示

**Context**: 现有流水保存了资金分配 `allocation`，但没有保存交易后的钱袋余额；历史回算会受到同日顺序、删除和旧数据演进影响。

**Decision**: 新流水保存并显示精确的交易后余额。旧流水只展示已有资金流向，不回算余额、不显示余额，也不增加缺失提示。

**Consequences**: 详情不会展示可能错误的历史余额；新旧流水的内容丰富度会自然不同，但界面不额外强调这种差异。

### 钱袋展示范围

**Context**: 一笔交易通常只影响部分钱袋，固定展示所有钱袋会产生大量零变化信息。

**Decision**: 详情只展示实际发生金额变化的钱袋。新流水的每个变化项同时显示流入或流出金额以及交易后的余额；旧流水只显示变化金额。

**Consequences**: 详情更紧凑，资金路径更突出；未变化钱袋的余额不在该笔详情中展示。

### 详情与删除入口

**Context**: 当前流水列表已有删除按钮，新增详情后需要避免整行点击与删除操作冲突。

**Decision**: 不新增详情按钮，点击流水条目的其他区域打开详情；删除按钮继续只保留在列表中，详情内不提供删除入口。

**Consequences**: 列表结构变化较小；实现时删除按钮必须阻止点击事件冒泡，避免删除操作同时打开详情。

### 本周与后续周预算

**Context**: `allocation.week` 和 `allocation.advance` 都会减少 `pockets.spendable`，但业务含义不同；合并后无法判断一笔支出是否提前使用了后续周预算。

**Decision**: 详情将二者分别展示为“本周预算”和“后续周预算”。新流水分别保存可展示的交易后本周剩余与后续周可用余额。

**Consequences**: 用户能直接审计跨周提前消费；余额快照不能只保存四个底层钱袋，还需要保存周维度的派生余额。

### 收入的生活预算去向名称

**Context**: 收入的 `allocation.week` 可能建立整个周期的周预算或增加当前周期可用金额，语义不同于支出侧的“本周预算”。

**Decision**: 收入详情将该去向显示为“可消费余额”。支出详情仍分别使用“本周预算”和“后续周预算”。

**Consequences**: 收入去向与总览口径一致；同一底层 allocation 字段会根据交易类型使用不同的用户文案。

### 资金不足的交易

**Context**: 当前部分支出路径允许交易金额超过所有可用资金，保存的实际扣款分配可能无法覆盖交易总额。

**Decision**: 详情将交易金额与实际资金来源合计之间的正差额显示为“资金缺口”。本任务不阻止此类交易，也不修改原有分配规则。

**Consequences**: 详情能够如实对账；用户会看到现有数据中潜在的余额不足情况，但该问题的记账策略需要另行处理。

### 资金流视觉表达

**Context**: 普通金额列表可以展示变化，但不能快速表达收入分流、支出汇流和内部结转的方向。

**Decision**: 详情采用轻量箭头流。收入由总金额指向各分配去向；支出由各扣款来源指向支出总额；系统结转由转出资金指向各转入钱袋。每个变化项同时承载变化金额和可用的交易后余额。

**Consequences**: 资金方向可快速识别；实现应保持移动端紧凑，不采用复杂 Sankey 图或可拖拽节点。

### 历史变更后的余额快照

**Context**: 删除较早的交易会改变当前钱袋状态；如果重新计算后续交易的余额，需要可靠重放所有历史流水，但旧数据缺少稳定顺序和完整快照。

**Decision**: 每笔新流水保存的交易后余额是不可变快照，表达该笔交易原始发生时的结果。删除或回滚其他历史交易不修改它。

**Consequences**: 单笔详情保留当时的真实记录；用户修改历史后，旧快照不一定与重新排列后的剩余交易推导结果一致，但不会被不可靠的回算篡改。

### 历史列表加载

**Context**: 当前事件数据在计算阶段被截断为最近 10 条，导致“查看全部”无法访问更早流水；一次渲染全部历史又可能形成过长的移动端列表。

**Decision**: 历史弹层初始展示 20 条，底部提供“加载更多”，每次增加 20 条直至全部展示。加载数量只保存在组件 UI 状态中。

**Consequences**: 所有历史流水最终均可查看，同时控制初始渲染长度；需要将“最近三条”与“完整排序历史”拆成不同派生数据。

### 历史列表与详情弹层关系

**Context**: 用户可能连续核对多条历史流水，需要在详情关闭后继续停留在原列表位置。

**Decision**: 历史弹层保持打开，详情作为第二层弹层覆盖其上。关闭详情只移除上层，恢复下层历史列表。

**Consequences**: 列表加载状态和滚动位置易于保留；实现必须处理双层遮罩、z-index、焦点和关闭事件隔离。

### 创建时间

**Context**: 现有交易只有账目日期，同日多笔流水无法在详情中明确区分创建顺序；交易 ID 虽以当前时间为基础，但不是正式的可展示时间契约。

**Decision**: 新流水保存不可变的 ISO `createdAt`，详情显示账目日期和创建时间。同日新流水优先按 `createdAt` 排序；旧流水缺少该字段时保持兼容并只显示日期。

**Consequences**: 新记录具备更明确的审计顺序；系统补做结转时，账目日期仍表示应结转日期，创建时间表示实际生成记录的时间。

### 交易后余额存储

**Context**: 历史重放依赖完整、稳定且不可变的事件序列，现有旧数据和删除能力无法保证这一点；独立审计表又会增加本地存储同步负担。

**Decision**: 在 `DailyTransaction` 内保存可选、不可变的 `balanceAfter`。`allocation` 继续负责资金流、统计和回滚；快照只服务详情展示。

**Consequences**: 新流水能精确展示交易后余额并保持旧数据兼容；所有创建交易的路径都需要生成快照，复合操作必须逐笔计算中间状态。

## UI Design Specification

1. **Purpose Statement**: 为生活预算流水提供移动端优先的只读审计详情，让用户在一次点击后理解交易类型、总额、资金来源或去向，以及新流水发生后的相关余额。详情应优先保证准确与可扫读，而不是提供编辑能力。
2. **Aesthetic Direction**: Brutally minimal（克制、账本式、强调数字与方向）；沿用项目现有生活预算设计系统，不引入独立视觉主题。
3. **Color Palette**: 沿用既有 token：正文 `#26342f`、主蓝 `#427987` / `#91c7d1`、缓冲绿 `#5f8d62` / `#95c79a`、警示琥珀 `#d9b76c`、缺口红 `#d88b7f`，并适配现有深色主题变量。
4. **Typography**: 沿用项目品牌字体 `Noto Sans SC`；金额使用现有粗字重和紧凑数字排版，不新增字体依赖。
5. **Layout Strategy**: 复用现有 `BottomSheet`。顶部以偏左的大金额和交易元数据作为视觉锚点；中部使用纵向流向轨道与轻量箭头，变化钱袋按资金方向排列；交易后余额作为每个变化项的次级信息。手机端单列，桌面端保持窄幅账本阅读宽度。
6. **Icons and Motion**: 只使用项目现有 Lucide 图标；弹层复用现有淡入/上移动效，不新增装饰性动画。
7. **Brand Override**: 项目已有明确配色、字体和 BottomSheet 组件，优先于通用 UI 技能的字体与布局禁用项，避免与现有产品割裂。
